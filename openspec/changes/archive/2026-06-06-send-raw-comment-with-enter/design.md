## Context

评论派发当前由 `src/app.js` 构造结构化 prompt，再通过 `src/terminal.js` 的终端控制器写入运行中的 Agent 会话。单条评论和批量历史注释都会附带任务标记、文档路径、被评论原文、上下文和处理指引；终端控制器负责统一做会话可用性校验并写入终端。

本次变更要求评论发送时只传递用户评论内容本身，且写入后自动提交 Enter，让 Agent 可以直接开始处理。

## Goals / Non-Goals

**Goals:**

- 单条评论派发只发送该条 `annotation.note` 的内容。
- 历史批量派发只发送选中评论的 `annotation.note` 内容集合，不附加路径、引用、上下文、编号任务说明或处理指引。
- 保持终端控制器在成功写入内容后自动补充 Enter 的行为，并将该行为纳入需求约束。
- 保留现有 Agent 可用性校验、空内容校验、发送失败反馈和评论本地保存语义。

**Non-Goals:**

- 不改变评论保存的数据结构。
- 不改变 Agent 会话启动、选择、状态展示或可用性判定逻辑。
- 不新增评论编辑、模板选择或高级 prompt 配置能力。

## Decisions

- **在评论派发构造层剥离附加信息。** 将 `buildSingleAnnotationPrompt()` 调整为仅返回清理后的评论内容；将 `buildBatchAnnotationPrompt()` 调整为只合并选中评论内容。这样所有现有入口继续复用 `dispatchAnnotationToAgent()` / `dispatchHistoryBatchToAgent()`，避免在抽屉、自动发送、历史单条和历史批量入口中复制逻辑。
- **保留终端控制器作为提交边界。** Enter 键提交应由 `dispatchPrompt()` 统一保证，而不是由上层 prompt 构造函数拼接回车字符。这样可用性校验、空内容校验和实际写入行为仍集中在终端控制器中。
- **批量内容仅合并评论正文。** 对多条选中评论使用简单分隔（例如空行）拼接评论正文，不加入编号、文档路径或“批量任务”说明，满足“不添加任何信息”的要求。

## Risks / Trade-offs

- **上下文缺失可能降低 Agent 理解准确性。** → 按用户要求优先保持原始评论内容；如用户需要上下文，应直接在评论内容中写明。
- **批量发送多条评论时边界较弱。** → 使用最小分隔符分隔多条评论正文，避免新增语义信息，同时保留可读性。
- **已有测试或验证可能假设结构化 prompt。** → 更新相关验证，确保不再检查任务标记、路径和上下文字段。
