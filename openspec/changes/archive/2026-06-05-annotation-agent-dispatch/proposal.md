## 为什么要做

当前 Markdown 浏览器里的评论能力更像“本地记录”，而 AI 终端更像“即时执行器”，两者之间还没有稳定的桥接。用户在实际使用时会出现两种不同诉求：

- 有些评论只是临时想法，希望先保存，不要立刻打扰 Agent。
- 有些评论已经足够明确，希望保存后马上派发给 Agent 处理。

此外，历史注释目前只能查看、复制和打开，不能把已经沉淀下来的评论再次转化成 Agent 任务，这让“评论作为任务池”的价值没有发挥出来。

因此，这次变更要把评论系统从“纯记录”升级为“记录 + 可配置派发 + 历史重派发”的工作流。

## 变更内容

- 新增一个全局配置，用于控制“评论保存后是否自动发送给 Agent”，并将该配置保存在本地浏览器存储中。
- 该全局配置放在 Markdown 浏览相关控制区，而不是评论抽屉内部，使其语义保持为“全局默认策略”而不是“单条评论字段”。
- 在评论抽屉中保留“保存”动作，同时新增“发送给 Agent”动作。
- 评论抽屉中的按钮语义明确区分为“仅保存”和“发送给 Agent”，避免用户误解保存动作一定会派发任务。
- “保存”始终先保存到本地；若全局自动发送开启，则保存成功后自动尝试派发给 Agent。
- “发送给 Agent”始终先保存到本地，然后强制尝试发送给 Agent，不受全局配置影响。
- 在历史注释页面中支持选择部分注释，并将所选注释一键发送给 Agent。
- 为历史注释提供单条发送与批量发送入口，使历史注释可以重新转化为 Agent 任务。
- 历史注释的批量发送以一次合并 prompt 的方式提交给 Agent，而不是对每条评论逐条写入终端。
- 历史注释的“按文档”视图支持勾选发送；“单行文本”视图继续保持轻量复制用途，不承载勾选发送交互。
- 当当前没有可用的运行中 Agent 会话时，发送失败不得影响评论保存，系统需要给出明确反馈。
- 第一版优先面向明确支持任务派发的 Agent 会话；对于不具备可靠派发语义的自定义命令，会话可用性由终端控制器统一判定。
- 统一定义单条发送、批量发送、自动发送的 prompt 结构，确保 Agent 能理解这是来自 Markdown 评论的任务上下文。
- 统一定义发送过程中的按钮禁用、重复点击防护、toast 文案、选择态重置、批量上限与内容裁剪策略。
- 保持发送动作即时执行：如果当前没有可派发的 Agent，会直接提示失败，不创建后台队列，也不隐藏待处理状态。

## 能力范围

### 新增能力

- `annotation-agent-dispatch`：让评论与历史注释可以按照全局策略或显式按钮操作发送给运行中的 Agent。

### 修改能力

- 修改现有评论保存流程，使其支持“仅保存”和“保存后派发”两种路径。
- 修改历史注释页面，使其从纯展示升级为可选择、可发送的任务入口。

## 影响范围

- 前端全局状态与本地配置持久化：`src/app.js`
- 评论抽屉交互与按钮行为：`index.html`、`src/app.js`
- 历史注释渲染与选择发送交互：`src/history.js`、`src/app.js`
- Agent 终端派发桥接能力：`src/terminal.js`
- 可能需要少量样式调整以承载新增按钮、勾选态和批量操作入口：`styles/*.css`

## 非目标

- 本次不引入“待发送队列”或离线补发机制。
- 本次不要求在历史注释的单行文本模式下支持勾选发送。
- 本次不要求建立评论与 Agent 回复之间的结构化双向关联。
- 本次不新增新的后端派发 API，优先复用现有前端到终端的会话桥接能力。
- 本次不尝试解析 Agent 输出、判断任务是否真实完成，也不将 Agent 执行结果写回注释记录。
- 本次不把自动发送配置同步到服务端或跨浏览器共享，该配置仅作为当前浏览器本地偏好。
