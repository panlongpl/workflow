## 背景

当前项目已经具备两套相对独立的能力：

1. Markdown 原文评论能力：用户可以选中文本、填写评论并保存到本地注释存储。
2. AI 终端能力：用户可以启动一个真实的 Agent 终端会话，通过 WebSocket 与 PTY 进程交互。

评论保存入口集中在前端，终端会话控制也集中在前端，因此最自然的扩展方式不是新增一个后端任务编排层，而是在前端完成“评论保存成功后，按策略决定是否派发到 Agent”的桥接。

## 目标

- 让用户可以通过全局配置决定“保存评论后是否默认自动发送”。
- 让评论抽屉支持显式“发送给 Agent”，并保证该动作总是先保存、后发送。
- 让历史注释页面支持从既有评论中选出部分内容重新发送给 Agent。
- 在没有运行中 Agent 会话时，保存与发送的结果反馈保持清晰且互不污染。
- 统一 prompt 模板、反馈文案、重复点击防护、批量限制和选择态规则，让实现阶段不再需要重新解释产品边界。

## 非目标

- 不实现后台任务队列、重试队列或延迟补发。
- 不改变注释持久化结构的核心语义，仍以本地注释为事实来源。
- 不在第一版中实现复杂的 Agent 忙闲检测或输入时机推断。
- 不解析 Agent 输出，不判断 Agent 是否完成，也不把处理结果写回历史注释。
- 不为自动发送配置增加后端存储或跨设备同步。

## 设计决策

### 1. 用本地配置控制默认派发策略

新增一个本地持久化配置，例如 `annotationAutoSend`，用于记录用户是否希望“保存评论后自动发送给 Agent”。

默认值建议为关闭，理由是：

- 更符合“评论先是记录、再可能是任务”的使用习惯。
- 可以避免用户输入尚未完成时误触发 Agent。
- 用户仍然可以通过显式“发送给 Agent”按钮立即派发。

该配置在界面上的位置应尽量靠近现有 Markdown 浏览控制区，例如与“原文 / AI 阅读版 / 历史注释”和“阅读模式”处于同一控制层。这样用户更容易理解它控制的是整个 Markdown 评论工作流，而不是当前抽屉内某一条评论的属性。

### 2. 把“保存”和“发送”定义为两个清晰动作

评论抽屉需要同时支持两个动作：

- **仅保存**：始终保存到本地，是否发送取决于全局配置。
- **发送给 Agent**：始终先保存到本地，再强制尝试发送。

这样可以保证：

- 所有发送出去的评论都能留痕。
- 用户不会遇到“发出去了但本地没有记录”的不一致状态。
- 用户可以显式区分“记一下”和“交给 Agent 做”。

按钮文案建议直接采用：

- `仅保存`
- `发送给 Agent`

而不是模糊地使用“保存”“发送”，以降低歧义。

### 3. 历史批量发送采用“单次合并 prompt”而非逐条写入终端

对历史注释做批量发送时，不应将多条评论逐条写入 PTY，因为终端 Agent 当前是否空闲不可可靠判断，连续写入多条 prompt 容易造成交错输入。

因此，批量发送时应把选中的评论合并成一个统一 prompt，一次性发送给 Agent。

优点：

- 降低 PTY 输入乱序和交错的风险。
- 让 Agent 一次性获得完整上下文，便于统一分析优先级。
- 前端逻辑更简单，也更容易给出单次成功/失败反馈。

### 4. 历史页的“可选择发送”仅在按文档视图中支持

历史注释目前有“按文档”和“单行文本”两种展示方式。单行文本模式的主要目标是复制，不适合承载逐项勾选和批量交互。

因此第一版中：

- “按文档”模式支持勾选、单条发送、批量发送。
- “单行文本”模式继续保持轻量复制视图，不增加勾选逻辑。

在“按文档”模式下，推荐交互为：

- 页头提供“发送选中项给 Agent”批量入口。
- 每条历史注释提供勾选框。
- 每条历史注释同时保留“打开”和“发送”动作。

这样可以同时覆盖“只发一条”和“挑几条一起发”的两种使用路径。

### 5. 没有可用 Agent 时，发送失败不影响保存结果

发送只是评论保存之后的附加动作，不能反向影响评论落盘结果。

因此：

- 对评论抽屉而言：如果保存成功但没有运行中的 Agent，会提示“已保存，但未发送”。
- 对历史注释发送而言：因为该动作本身不涉及新保存，所以可以直接提示“当前没有运行中的 Agent”。

### 6. 由终端控制器统一判定当前会话是否允许派发

并不是所有终端会话都天然适合接收结构化评论任务。尤其是自定义命令模式下，用户可能启动的是普通 shell 或其他交互程序，而非支持任务提示词的 Agent。

因此，发送能力不应由评论页面直接假设“只要 socket 连着就能发”，而应由终端控制器统一暴露一个“当前会话是否允许派发”的判断结果。第一版设计上应满足：

- 明确支持的 Agent 会话可以接收评论派发。
- 无法可靠识别的会话类型可以返回“当前会话不可派发”的结果。
- 评论页面和历史页面只消费统一的可派发性结果，不自行判断底层终端细节。

### 7. 自动发送只作为保存成功后的附加动作

自动发送不能改变保存动作的主结果。无论发送成功、失败或不可派发，只要本地保存已经成功，评论就应留在本地历史中。

因此实现时应避免把“保存 + 自动发送”包装成一个不可拆分事务。推荐顺序为：

1. 校验评论内容。
2. 保存到本地。
3. 更新当前视图与历史数据状态。
4. 如果需要发送，则尝试派发。
5. 根据保存结果与发送结果给出组合反馈。

### 8. 发送操作需要防重复点击

评论抽屉的“仅保存”“发送给 Agent”，以及历史页的“发送”“发送选中项给 Agent”，都属于可能产生副作用的操作。

第一版应在操作进行中临时禁用对应按钮，避免用户连续点击导致：

- 同一评论被重复保存。
- 同一 prompt 被重复写入 Agent。
- 历史批量发送重复提交。

禁用只需覆盖当前动作生命周期，不需要引入全局锁。

```text
├──────────────────────────────┤
│ 引用内容                      │
│ ……                           │
├──────────────────────────────┤
│ 评论输入框                    │

├──────────────────────────────┤
│ [删除] [仅保存] [发送给 Agent] │
└──────────────────────────────┘
```

### 全局配置

```text
[ ] 保存评论后自动发送给 Agent
    默认关闭；开启后点击“仅保存”也会在保存成功后尝试发送。
```

### 历史注释（按文档）

```text
页头： [发送选中项给 Agent] [复制全部]    已选 2 条

[ ] 注释 A   [打开] [发送]
[ ] 注释 B   [打开] [发送]
[ ] 注释 C   [打开] [发送]
```

## 行为矩阵

### 评论抽屉动作

| 用户动作 | 保存本地 | 是否发送 | 发送依据 | 失败处理 |
| --- | --- | --- | --- | --- |
| 仅保存，自动发送关闭 | 是 | 否 | 全局配置关闭 | 仅反馈保存结果 |
| 仅保存，自动发送开启 | 是 | 是 | 全局配置开启 | 保存成功不回滚，提示发送结果 |
| 发送给 Agent | 是 | 是 | 显式动作强制发送 | 保存成功不回滚，提示发送结果 |
| 删除 | 否 | 否 | 不涉及发送 | 保持现有删除语义 |

### 历史注释动作

| 用户动作 | 是否保存 | 是否发送 | 备注 |
| --- | --- | --- | --- |
| 单条发送 | 否 | 是 | 使用历史中已保存的注释内容 |
| 发送选中项 | 否 | 是 | 多条合并成一次 prompt |
| 打开 | 否 | 否 | 保持现有定位到原文注释行为 |
| 复制全部 | 否 | 否 | 保持现有复制行为 |

## UI 文案与反馈

### 固定按钮文案

- 全局配置：`保存评论后自动发送给 Agent`
- 评论抽屉保存按钮：`仅保存`
- 评论抽屉显式发送按钮：`发送给 Agent`
- 历史页批量发送按钮：`发送选中项给 Agent`
- 历史页单条发送按钮：`发送`

### Toast 文案建议

| 场景 | 文案 |
| --- | --- |
| 仅保存成功，未触发发送 | `记录已保存。` |
| 保存成功且发送成功 | `记录已保存，并已发送给 Agent。` |
| 保存成功但没有运行中 Agent | `记录已保存，但当前没有可用的 Agent，未发送。` |
| 保存成功但当前会话不可派发 | `记录已保存，但当前终端会话不可用于评论派发。` |
| 保存失败 | `保存记录失败。` |
| 显式发送成功 | `已发送给 Agent。` |
| 历史未选择任何注释 | `请先选择至少一条历史注释。` |
| 历史批量发送成功 | `已将选中的 {count} 条注释发送给 Agent。` |
| 历史批量超出上限 | `一次最多发送 {limit} 条注释，请减少选择后重试。` |

如果具体错误来自底层异常，toast 可以追加或替换为更具体的错误信息，但不应暴露不可理解的技术细节。

## 选择态与重置规则

- 历史注释选择态只存在于前端 UI 状态中，不写入注释存储。
- 选中集合以稳定 key 维护，推荐使用 `rootPath + path + annotation.id` 组合，避免不同文档中 ID 冲突。
- 从历史页离开到原文/AI 阅读版时，清空选中集合。
- 从按文档模式切换到单行文本模式时，清空选中集合。
- 历史数据重新加载后，应移除已经不存在的选中项。
- 批量发送成功后，清空已发送的选中项。
- 批量发送失败时，保留选中项，方便用户启动 Agent 后重试。

## 派发可用性

终端控制器需要对外暴露足够简单的结果，供评论系统和历史页消费。建议形态为：

```text
canDispatchToAgent() -> {
  ok: boolean,
  reason?: "no-session" | "starting" | "closed" | "unsupported-agent" | "socket-not-open"
}

dispatchPrompt(prompt) -> {
  ok: boolean,
  reason?: string
}
```

第一版可派发会话建议限定为：

- 已启动且 WebSocket 仍打开的 `codex` 会话。
- 已启动且 WebSocket 仍打开的 `claude` 会话。

`custom` 会话默认不可派发，除非实现阶段增加显式 allowlist 或用户确认机制。本次 proposal 不要求实现 custom allowlist。

## 数据与状态

### 新增前端状态

- `annotationAutoSend`: 是否开启“保存后自动发送”
- `selectedHistoryAnnotationIds`: 历史注释页当前选中的注释集合
- `historySelectionMode`（可选）：如果实现阶段发现需要区分“按文档视图下的选择态重置策略”，可单独建模为局部 UI 状态，而不是混入注释数据本身
- `annotationDispatchPending`: 评论抽屉当前是否正在执行保存/发送动作
- `historyDispatchPending`: 历史页当前是否正在执行单条或批量发送动作

### 本地存储

- 建议使用版本化 key，例如 `markdown-viewer-annotation-auto-send-v1`。
- 存储值只需要表达布尔偏好，例如 `"true"` / `"false"` 或 JSON `{ "enabled": true }`。
- 读取失败、解析失败或值缺失时统一回退为关闭。

### 复用现有注释结构

发送给 Agent 的上下文继续复用现有注释信息，不新增新的注释存储字段：

- `quote`
- `note`
- `contextBefore`
- `contextAfter`
- 文档路径 / 根目录路径

## Prompt 组织策略

### 单条发送

单条评论发送时，prompt 应包含：

- 工作目录
- 文档路径
- 引用内容
- 评论内容
- 前后文
- 固定引导语

建议固定引导语明确告诉 Agent：这是来自 Markdown 评论的任务，请优先判断是“文档修订”“代码修改”还是“解释说明”，避免 Agent 将评论仅当作普通聊天输入处理。

建议模板：

```text
[MARKDOWN_COMMENT_TASK]
你正在协助处理一条来自 Markdown 浏览器的评论任务。

工作目录：{rootPath}
文档路径：{path}

被评论的原文：
{quote}

用户评论：
{note}

前文上下文：
{contextBefore}

后文上下文：
{contextAfter}

请基于以上信息自行判断下一步：
1. 如果这是文档修订任务，请直接修改或说明建议修改内容。
2. 如果这是代码/项目任务，请定位相关文件并继续处理。
3. 如果信息不足，请说明缺少什么信息。
```

### 批量发送

历史批量发送时，prompt 应按编号聚合多个注释，统一提交给 Agent，例如：

```text
以下是从 Markdown 历史注释中选出的多条待处理评论，请统一分析并按优先级处理：

1. 文件 … / 引用 … / 评论 …
2. 文件 … / 引用 … / 评论 …
3. 文件 … / 引用 … / 评论 …
```

如果实现阶段发现批量内容过长，应优先采用“限制单次发送数量”或“裁剪过长上下文”的方式控制 prompt 规模，而不是退回逐条连续写入终端。

建议模板：

```text
[MARKDOWN_COMMENT_BATCH_TASK]
以下是从 Markdown 历史注释中选出的 {count} 条待处理评论。请统一分析，按优先级处理；如果需要修改代码或文档，请直接继续。

工作目录：{rootPathSummary}

## 注释 1
文档路径：{path}
被评论的原文：
{quote}
用户评论：
{note}
前文上下文：
{contextBefore}
后文上下文：
{contextAfter}

## 注释 2
...
```

### 内容规模建议

- 单次批量发送默认最多 20 条注释。
- 单条 `quote` 建议最多保留 1200 字符。
- 单条 `note` 建议最多保留 2000 字符。
- `contextBefore` 与 `contextAfter` 各建议最多保留 800 字符。
- 裁剪时应保留开头内容并追加 `…（已截断）`，让 Agent 知道上下文不完整。

这些数值不是协议要求，但应在实现中保持集中配置，方便后续调整。

## 可访问性与键盘行为

- 新增开关应使用明确 label，不能只依赖 title。
- 历史注释的复选框应支持键盘聚焦与空格切换。
- “发送选中项给 Agent”在没有选中项时可以禁用，但仍应有可理解的提示或可见计数。
- 新增按钮应保持与现有按钮一致的焦点样式。
- 评论抽屉关闭、保存、发送后应保持现有焦点体验，不强制跳转到 AI 终端。

## 发送后是否切换到终端

第一版不自动切换到 AI 终端。理由是：

- 用户可能正在连续阅读和记录多条评论。
- 自动切换会打断 Markdown 浏览上下文。
- 用户可以通过顶部模块切换主动查看 Agent 处理过程。

发送成功 toast 可以提供动作入口，例如“查看终端”。如果实现成本较高，第一版也可以只提示已发送。

## 错误处理策略

- 保存失败：不发送，显示保存失败。
- 保存成功但发送失败：保留保存结果，显示发送失败原因。
- Agent 会话不存在：不创建队列，提示当前没有可用 Agent。
- Agent 会话不可派发：不写入终端，提示当前会话不可用于评论派发。
- 发送过程中 socket 断开：提示发送失败，用户可重新启动 Agent 后从历史注释再发。
- 批量选择为空：不发送，提示先选择注释。
- 批量超出上限：不发送或按明确裁剪策略发送；若采用上限阻止，提示用户减少选择。

## 实现分层建议

- `src/terminal.js`：只负责会话状态、可派发性判断、向终端写入 prompt。
- `src/app.js`：负责评论保存流程、自动发送策略、prompt 组装、toast、历史选择态。
- `src/history.js`：负责历史页展示、勾选 UI、单条/批量动作回调，不直接访问终端。
- `index.html`：承载新增全局开关与评论抽屉按钮。
- `styles/*.css`：补充开关、历史选择态、按钮排列样式。

该分层可以避免历史页直接耦合终端，也避免终端控制器理解注释业务结构。

## 风险与权衡

- **风险：Agent 当前正在处理中，新的 prompt 可能插入到非理想时机。**
  - 取舍：第一版不做复杂时机检测，先保证能力可用与反馈清晰。

- **风险：自定义终端命令未必真的是 Agent。**
  - 取舍：实现阶段应由终端控制器显式判断当前会话是否允许派发，避免盲发到普通 shell。

- **风险：历史批量发送的 prompt 可能过长。**
  - 取舍：优先限制单次批量发送规模，并保证合并发送策略不退化为逐条 PTY 写入。

- **风险：历史页交互变复杂。**
  - 取舍：只在按文档视图增加勾选与发送，单行模式保持轻量。

- **风险：用户误解“保存”与“发送”的区别。**
  - 取舍：通过清晰文案（如“仅保存”“发送给 Agent”）降低歧义。

- **风险：发送成功但用户看不到 Agent 是否开始处理。**
  - 取舍：第一版只保证 prompt 成功写入会话；是否处理完成由用户在 AI 终端中观察。

- **风险：自动发送开启后用户忘记该配置。**
  - 取舍：配置常驻 Markdown 控制区且默认关闭，降低意外发送概率。
